# 2.4 知识管理组：知识评审者

## 2.4.1 问题

知识写出来了，下一步是判断它好不好。

这件事在代码上做过很多年，叫 code review。现在这一关大半交给 AI 了：逐行读别人代码的人越来越少，人类工程师已经很少判断一段代码写得好不好。

但还有一样东西必须判断，是知识本身。

没有人能对 AI 的产出做全量判断。

这一节不假设存在一个"什么都能判"的人，就算存在，判断这些海里的知识也会极大的消耗他的精力。它要解决的是：在判断力有限的前提下，评审怎么设计。

## 2.4.2 和 code review 是同一件事

知识点评审和 code review 干的是同一件事：在被使用之前，找出哪儿不对。

区别在受众。代码的受众是编译器和业务，知识的受众是 AI，还有读它的人。

## 2.4.3 第一种要排除的人

不能让写这段代码的人来审自己的代码。不是水平问题，是视角问题：他脑子里有全部上下文，读自己写的东西，会自动把漏掉的部分补上。

知识一样。作者读自己的规范，读到的常常是他想写的那句，不是纸上那句。

所以第一个要排除的，是技术专家在他自己那块知识上做判断。他的判断力有用，只是不能用来审自己。

## 2.4.4 第一评审者：AI

知识是写给 AI 的，那最硬的判据就是 AI 用得怎么样。

同一件事做两遍：一次不给知识，一次给。比三样东西——写得快不快、返工几次、产出合不合既有写法。

给了以后明显更好，这份知识就是好的；给了以后没变化，多半是它写了模型本来就会的常识；给了以后更差，那就是错的。

这个判据比人的主观评价靠得住，因为它能重复：换个人跑，结果差不多。

## 2.4.5 第二评审者：工程师

但 AI 是工具，不能全信。

它最麻烦的地方是错得很整齐：一份错的知识，它会在十个页面里用同一种方式错，看起来还挺一致。

所以工程师还得自己做一步：读一遍规范，再读 AI 的产出，对照。

## 2.4.6 分层放行

把"该做哪些检查"定下来，靠的是按风险分层，不是按代码行数。

| 风险 | 例子                         | 人工介入 |
| --- |------------------------------| --- |
| 低 | 脚手架、注释、文档、测试样例 | AI 自跑，事后抽查 |
| 中 | 一般业务逻辑、查询、报表     | 抽检，抽检不通过则全查 |
| 高 | 技术底座代码                 | 双人评审，其中一人熟悉这条链路 |

## 2.4.7 两份读者，一份知识

所以评审者有两方：AI，和经验丰富的工程师。

其实是一码事，因为人好理解的文档，AI 理解起来肯定也不差，反之亦然。

## 2.4.8 结论

评审不是打分，是在这份知识被复制到全组之前，先把它压到能用的形状。

唯一的判断依据就是：AI 用了之后是不是少返工，真的让整个项目组提效了。
